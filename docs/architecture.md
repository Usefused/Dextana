# Architecture

```text
React desktop renderer
  └─ validated Electron IPC through sandboxed preload
      ├─ Activities: backend commands and snapshot subscription
      ├─ LocalCapabilities: approvals and local resource enforcement
      ├─ Store: settings, keyring references, browser state and UI metadata
      ├─ Browsers: isolated WebContentsViews, native input and clipboard
      └─ Runtime: authenticated compiled backend with private Python
          └─ Harnest managed ADK agent
              ├─ Activities: runs, queues, steering, workers and plans
              ├─ SQLite: transcripts, receipts, sessions and checkpoints
              ├─ Scheduler: evaluation, dispatch and result collection
              ├─ Harnest MCPClient: HTTP / stdio sessions and execution
              └─ per-invocation Ollama routing through LiteLLMLifecycle
```

## Ownership and concurrency

There is one owner identity. No organization, workspace membership, roles, or account server is required. Model selection and Ollama routing are captured in each activity and sent as non-secret request metadata to Harnest. The model routing hook runs against the active invocation context, never mutable global provider settings.

Each desktop activity maps to a Harnest session. Harnest owns that session's model conversation and checkpoints through Dextana's custom SQLite store. The backend also owns the human-visible transcript, run status, queued messages, plan state and action receipts. Electron subscribes to snapshots and merges its local browser, folder and permission metadata. Concurrent activities share the Harnest process while isolating invocation state. A backend activity accepts one active turn at a time, with up to eight concurrent activities and FIFO follow-ups. The HTTP listener permits 64 connections so live sockets, MCP calls, control requests and polling cannot exhaust the eight-run budget. Steering cancels the active turn before applying the selected queued message; other queued messages remain paused on cancellation.

The lifecycle factory binds the same `SQLiteStore` instance to sessions and checkpoints. The packaged backend writes `agent-state/agent.sqlite` inside the owner's application-data directory; it needs no database server or extra Python package. Standalone Harnest development uses `.harnest/state/agent.sqlite` unless `DEXTANA_STORAGE_DIRECTORY` is set. Construction performs no disk I/O. Lifecycle startup opens the database, and shutdown closes it without discarding state.

SQLite uses WAL and full synchronous commits, private file permissions, and a versioned schema. A kernel-held file lock permits one backend process per database. In that process, session leases serialize turns for the same session while independent sessions continue concurrently. Short session/checkpoint transactions run on a dedicated thread, not on the agent event loop, and never span model calls or approval waits. Checkpoint mutations enforce owner scope, run exclusivity, and revision/status comparisons. Audit events contain operations and outcomes, not conversation data.

Runs expire after fifteen minutes without streamed text/reasoning or tool progress, rather than after a fixed elapsed duration. Socket pings and usage metadata do not renew this deadline. Owner questions, explicit approvals and delegated-worker waits pause the parent idle clock; each worker keeps its own idle watchdog. Cancellation remains immediate. Harnest’s separate live transport and long-wait client tools retain a 24-hour ceiling; individual browser/network operation timeouts still apply. Dextana does not impose a fixed desktop-action count on a progressing run.

Completed conversations and proposed plans retain their Harnest session IDs across restarts. A missing legacy memory-store session is reconstructed once from the backend's saved history; other storage failures are surfaced. Interrupted executions receive a fresh session, and startup marks abandoned running/waiting checkpoint runs failed while preserving their records. Pending actions are never replayed automatically. This desktop store implements the Harnest session and checkpoint contracts; optional distributed external-continuation and A2A task persistence are not implemented.

Outgoing model requests exclude earlier thinking/reasoning content. Before each request, the routing hook budgets the complete input, including tool schemas, restored history, recalled personal memory and image allowances. Ollama discovery prefers the running model's `/api/ps` context allocation, then `num_ctx` configuration; cloud models use their advertised context window. Compatible endpoints can advertise `context_length`, `context_window` or `max_model_len` in their model catalog. Discovery is cached for 60 seconds per connection and model. Recognized compatible models can also use the installed provider context metadata. Unknown context allocations, including unloaded local Ollama models, retain the independent byte guard rather than being assigned a fictional token window. Missing allocations are rechecked on the next request so a newly loaded model’s actual limit is picked up immediately. Limits are not silently increased. See [Ollama context allocation](https://docs.ollama.com/context-length).

The guard reserves output tokens, then allows input to occupy 90% of the remaining window. LiteLLM selects the model's tokenizer (with its generic fallback for unknown models), counting messages, tool schemas, image allowances and structured-output schemas. There is one 10% safety margin, without an additional token multiplier or a byte ceiling for known model windows. The 192 KB UTF-8 fallback applies only when the context limit is unknown. If token counting fails, request bytes conservatively estimate tokens against the discovered window. These are preflight estimates, not provider-reported input usage or a guarantee of exact tokenization for arbitrary compatible providers. Compatible catalogs can also supply `max_input_tokens` or a router's `top_provider.context_length`; the smaller advertised constraint wins. When the working history reaches the guard, a private Harnest `dextana_compactor` worker summarizes older records. Valid JSON chunk envelopes preserve record identity, fragment coverage and order; the reduction prompt forbids treating an incomplete fragment as a failed operation. A separate editorial pass reviews summaries that retain source-instruction commentary. It is a quality check, not a replacement for permission boundaries. Exact references, current corrections and action outcomes remain part of the summary contract.

The compactor uses the resolved model connection with ephemeral history, no tools, MCP clients or child agents, and Ollama thinking disabled. Its own inputs respect the same model window. Recent owner turns and system instructions remain intact; oversized current-turn results can be summarized without breaking tool call/result IDs. Full transcripts remain saved. Restored conversations enter the outgoing request as separate historical messages, rather than being embedded in the current owner's prompt.

Versioned compaction memory lives in the Harnest session application-data namespace. Matching prefix fingerprints and cached result replacements are applied before deciding whether another summary is needed, including after restarts or model changes. Edits invalidate mismatched memory. Calls have a 120-second deadline and two concurrent workers per activity. If summarization fails, explicitly labeled excerpts can still bound oversized assistant/tool text; owner input and system text are never silently cut. Requests that still cannot fit fail visibly.

Optional [personal memory](personal-memory.md) reuses this worker to produce both summaries and durable user facts. Exact record fingerprints let compaction reuse completed-turn summaries. The portable memory core accepts the existing activity database connection and injected embedding/extraction functions; a small host adapter handles turns, model context, invalidation and shutdown. Memory is enabled only after a configured embedding model passes an actual request. It does not require another database service or runtime dependency.

Static instructions precede recalled memories, and the live clock is appended after the working history. The clock is included in the input budget but excluded from durable records and compaction fingerprints. This keeps the preceding request prefix stable for providers that support prefix caching. Browser tool schemas carry compact operation guidance; detailed browser instructions are loaded through the browser-work skill and reused within the conversation. These reduce repeated overhead without lowering the model's context window.

`delegate` uses Harnest's typed client-tool protocol, with its caller inside the backend. The backend starts independent Harnest worker sessions and awaits their results in parallel. It enforces three workers per call, depth two, the shared eight-run limit, and parent cancellation. Each worker receives only the explicitly supplied assignment, not an implicit copy of its parent's session. Workers use the same agent definition and have their own browsers and MCP clients. Workers remain visible and cancellable in the app.

The backend persists orchestration in `agent-state/activities.sqlite`, independently of framework checkpoints. A first bootstrap imports legacy `state.json` activities only when the database is empty. After the import commits, Electron writes only local activity metadata to `state.json`. Future bootstraps cannot overwrite backend history with stale desktop snapshots. Interrupted runs and approved execution grants are invalidated on backend restart; completed history and proposed plans remain available.

Harnest 0.18 owns cron evaluation, the durable task queue, lease renewal, and worker dispatch. Dextana implements Harnest’s public `TaskStore` and `CronStore` contracts with one local SQLite provider in `schedules.sqlite`; sessions/checkpoints retain their separate store. Schedule advancement and task insertion commit atomically, and stale lease holders cannot finish work. No PostgreSQL or Redis server is required. The desktop’s `/dextana/jobs` routes retain authenticated CRUD and run-history presentation; the old custom polling loop, claim/report endpoints, and activity dispatcher are removed.

The agent’s `schedule` tool creates, lists, and removes these same visible jobs. A reminder requires a relative delay, a future timestamp with a UTC offset, or a recurring expression; an approved plan alone creates nothing. One-time jobs use native tasks with exact `scheduled_at` timestamps. Reminders append a durable message to the originating chat without requiring a model call, and Electron presents an in-app notice plus an operating-system notification when available. Scheduled work creates a fresh activity with ordinary approval boundaries; previous plan permissions are not carried into future executions. Editing or pausing a one-time job cancels its old queued task, and resuming queues a fresh definition.

Native Harnest schedules use UTC. UTC numeric expressions pass through directly; other time zones project their next local occurrence into a UTC schedule and re-arm after delivery, preserving daylight-saving behavior without a per-minute compatibility poll. Existing job IDs, paused state, and run history remain in the database while native schedule records are added. A committed dispatch receipt precedes activity creation, and the activity carries the same receipt identity so an interrupted handoff can be reconciled without replaying it. Scheduled activity tasks have zero automatic retries, overlap is skipped, and missed agent-work runs are skipped after restart or wake. Reminder occurrences instead catch up once, with overdue metadata and recurrence coalescing. Ordinary activity approval still gates local actions. Closing the window keeps the tray app and bundled backend running when background mode is enabled; explicitly quitting shuts them down. This does not install a background operating-system service. A separately hosted backend needs `DEXTANA_RUNTIME_TOKEN`, `DEXTANA_RUNTIME_URL` (its loopback listener URL), `DEXTANA_STORAGE_DIRECTORY`, and `DEXTANA_SCHEDULER_DIRECTORY`.

## Execution protocol

The backend orchestration service creates an authenticated Harnest session with `POST /sessions`, then connects that session to `/live` with the same owner token. A `response.create` frame starts the turn. Frames update only their originating activity. The backend handles delegation and plan transitions itself. Local actions become one-use broker requests bound to the activity. Electron validates and executes those requests, and the backend returns `client_tool.result` on the Harnest socket; subsequent model output continues streaming. The loop is bounded and never resubmits the initial user request to continue a tool call. Cancellation sends `response.cancel` and closes the connection.

The authored ADK plugin enables incremental model events, and the output policy exposes provider-supplied thinking separately from answer text. Thoughts expand while arriving and remain expanded through tool waits until answer text arrives or the turn ends. The stored duration adds thought phases and excludes tool waits. The owner can expand the grey thought panel after completion or restart. Models that do not emit thinking show only their answer.

Browser and MCP approvals are enforced in the main process before tool dispatch, including MCP connection and discovery. They belong to an exact activity and pending request. Decisions are consumed once; stale/cross-activity decisions fail, and cancellation removes the pending gate. Denial stops the turn instead of returning an error that the model could retry. Optional auto-allow is persisted separately for browser and MCP actions in each chat, after a successful save; workers do not inherit it. The owner can revoke it with Ask next time on the in-chat confirmation. A changed MCP endpoint invalidates an outstanding approval. Electron decrypts tokens and passes them directly to the authenticated backend connection endpoint; they are never model tool arguments or renderer state. MCP transport failures do not trigger execution retries.

Browser approval defaults live in **Settings → Browser use**. Chats without an explicit browser permission inherit the current global default, which initially asks for approval. A chat can choose **Use global default**, **Ask for approval**, or **Automatically approve** in Chat settings or the Browser use settings page. Explicit chat choices survive global changes and restarts. Session-wide Allow all takes priority; choosing Ask for approval again explicitly revokes browser auto-approval for that chat. Global changes neither accept pending approvals nor grant other capabilities, and unsaved defaults cannot authorize actions. Computer permissions and window selection live in **Settings → Computer use**; the close-window background preference lives in **Settings → Background service**.

Electron waits for the backend to commit an action-start receipt before dispatch and records a result receipt afterward. Outstanding broker requests are ephemeral and cannot be replayed after backend restart. A crash between these records leaves an explicitly uncertain outcome. Restarted conversations receive those receipts as context and are instructed not to replay earlier actions. This is not a transactional exactly-once guarantee across a desktop crash and external side effect.

## Dynamic MCP connections

`MCPConnections` in Electron owns encrypted credential access and per-tool policy enforcement. The backend creates Harnest `MCPClient.stdio` / `MCPClient.streamable_http` instances and their native ADK toolsets, with separate connections per activity. Harnest owns transport initialization, subprocesses, session pooling and teardown. The backend keeps decrypted credentials only in memory; they never enter transcript or checkpoint storage. Only the owner can save connections and policies through validated IPC. Cached discovery exposes enabled tools to the agent without network access. New/changed schemas default to disabled.

Custom MCP setup starts with a server URL, followed by an authentication modal and a searchable tool-permissions modal. HTTP connections support Bearer tokens, named headers (including `X-API-KEY`), unauthenticated endpoints, and a named top-level JSON body field for gateways that require it. Body authentication leaves JSON-RPC protocol fields and tool arguments intact; the gateway must support that field and session-based GET/DELETE requests. Auth placement is saved separately from the encrypted token. Changing placement resets tool permissions. Native HTTPX authentication injects credentials inside the backend; echoed tokens are redacted before discovery/results leave it.

Dynamic user connections use a small registry and authenticated desktop proxy. A pinned ADK compatibility boundary invokes the native toolset session executor because `get_tools()` drops pagination and transforms remote metadata; the bridge preserves cursors, exact schema fingerprints and raw results. It does not construct MCP sessions or transports. The HTTP lifecycle rejects redirects and disables inherited proxies; native stdio inherits a minimal environment. Tests cover paginated catalogs, schema drift, cancellation, per-chat process ownership and cleanup.

The managed agent's `mcp` tool calls an internal desktop client-tool helper to prepare one action. The desktop binds a single-use ticket to the activity, Harnest call ID, arguments, and connection revision. For tools marked `ask`, the agent enters `request_human_approval(action="mcp.execute", arguments=...)` around the exact execution. The backend relays `approval.requested` to the desktop and sends its `approval.decision`; only a matching `approval.resolved` grant releases the ticket. The internal helper is not a model-facing tool. A final live-schema/revision check precedes `callTool`. Disabled tools, stale tickets, cancellation, changed settings, and missing grants fail closed. Chat-wide auto-allow never enables disabled tools, and creating a native Fused token always requires separate approval.

## In-app browser

`WebContentsView` renders inside the main window alongside the conversation. The trusted renderer supplies the browser chrome; a native child view renders the untrusted page. Browser selection follows the owner's selected activity. Background runs create their own views without changing the selected pane.

Each activity saves its tabs and latest HTTP(S) pages on navigation and uses a stable, hashed persistent Chromium partition. Shutdown flushes browser storage and local metadata saves. Startup restores bookmarks (including migration from the previous visible page), without creating browser views or loading sites. The owner's Reopen browser action loads the saved address as a new navigation and restores the cursor; it never replays clicks or form submissions. Failed loads preserve a retryable bookmark. Cookies with persistent lifetimes and local storage survive restarts; session-only cookies, expired server sessions, unsent forms, and navigation history are not guaranteed to survive. Older ephemeral browser storage cannot be migrated after closing the old app.

The pane displays a tab strip across chats and delegated workers. A tab has a stable ID, owner activity, title, URL, and restore state. UI selection is independent of the agent’s default target; explicit `tab_id` arguments are checked against the calling activity. Implicit targets are fixed before the approval wait, so closing a tab never redirects a pending action. Browser calls remain approval-gated, including tab operations. Manual tab controls are explicit owner actions. Busy tabs cannot close mid-action. Each activity is limited to 12 tabs. Tabs share their owning activity’s storage partition; workers retain independent partitions. Closing a final tab is persisted without recreating it from historical context at startup.

Fixed isolated-world scripts produce bounded page text and element references. Fill/click operate only on references observed during the latest read and reject detached elements. The visible green cursor moves to the target before acting. Model-supplied values are serialized as data into these fixed scripts. No model-authored script, shell, or filesystem tool is exposed.

## Work files and context

The managed `files` client tool delegates to `WorkFiles` in Electron's main process. Preparation validates formats, sizes, table structure, and destination metadata without reading file contents. Activities obtains an exact read/create approval before execution, using separate `fileRead`/`fileCreate` chat capabilities. The preview is rendered as document text or sheet tables, not a code editor. Cancellation and denial reuse the existing approval lifecycle; permissions are persisted before auto-allowed dispatch.

PNG/JPEG/GIF/WebP reads validate raster signatures and return a typed `FileResult.image` using Harnest's `Image` contract. Harnest stages and delivers the media to the model; image bytes are not inserted into ordinary prompt text. Ollama capability discovery rejects reads with a clear message when the selected model lacks vision support. Word/PDF continue to use bounded text extraction, and sheets return literal values.

Reads use a bounded regular-file handle with no-follow, nonblocking flags; symlink leaf paths and special files are rejected. Workbook ZIP metadata and extracted table sizes have explicit limits, formulas/links are not evaluated. Creation uses exclusive creation with no-follow flags and never overwrites a file. The approved parent directory identity is checked again at execution. Paths from the native picker are normalized by resolving their parent, preventing macOS path aliases from creating duplicate context entries. The file picker also offers All files; additional formats can be read as UTF-8 text after ordinary read approval. Creation retains the work-document allowlist.

Editable-file reads return a SHA-256 revision. Text editing accepts UTF-8 files regardless of extension and requires that revision plus complete replacement content. DOCX and XLSX use targeted edits_json instead; package XML changes only the chosen Word text runs or existing Excel literal cells, plus workbook recalculation settings. All other ZIP parts remain unchanged. The local desktop binds the before/after preview to a regular-file snapshot and always requests a separate `fileEdit` approval; global access and approved plans cannot skip it. Before committing, it rechecks the content hash, file and parent identities, timestamps and mode, stages a complete sibling file, syncs it, and replaces the original by rename. Denial, cancellation before rename, stale revisions and failed writes leave the original intact. Same-process edits to a path are serialized by refusal; external changes are checked immediately before rename, although portable filesystem APIs cannot make that external comparison and rename a single atomic operation. Symbolic links, hard links, unsupported binary formats and non-UTF-8 text are rejected for editing. DOCX/XLSX editing validates ZIP/XML size limits and rejects entities, signed packages, protection and unsupported complex targets. The prepared replacement bytes and visible per-target changes are bound to the same approval.

Each Activity owns its persisted context references. Attachments on queued messages enter context only when their turn begins. The runtime receives reference metadata with an explicit untrusted-content boundary; selecting a path never reads contents. Successful file and browser results update context, as do HTTP(S) references in owner requests and final responses. Context controls expose only a validated external link or revealing a file already listed in that activity; embedded pages cannot call these IPC endpoints. No filesystem scanning, shell, file editing, or code-development tooling is provided.

## Everyday result presentation

`MarkdownContent` is shared by chat replies and A2UI Text. `RichTable`, `RichChart`, `RichImage` and `Diagram` provide the display components. Markdown `chart` and `mermaid` fences use these same components; A2UI adds data bindings and layout. The renderer never executes model-supplied HTML or JavaScript. Mermaid uses strict settings with configuration directives disabled and displays SVG inside isolated image documents. Remote raster previews use an explicit owner click and a size-limited, cookie-free main-process fetch; renderer network access remains disabled by CSP. Local file reads remain behind the file capability boundary.

The agent is instructed to explain outcomes in plain language, use tables where useful, and never echo tool payloads in normal replies. As a fallback, `readableResponse` converts JSON replies (whole, fenced, prose-wrapped, or double-encoded) into Markdown fields and tables. `readableData` unwraps MCP text results and presents document receipts using filenames and the Context affordance. Incomplete structured output is buffered behind “Preparing results…” while streaming; malformed output gets a recovery message. Values are escaped as display text. The stored response and runtime/tool payloads remain unchanged, so presentation cannot alter approvals or execution.

Browser and integration approval arguments use the same readable fields, preserving the requested values for review. Document approvals retain their text/table previews. Valid structured display cards still render; the conversation no longer offers a raw UI source inspector, and invalid/incomplete cards show a plain-language notice. Technical connection configuration remains available in Settings.


## Desktop interface

The managed `desktop` tool uses Harnest native `request_human_approval` and an internal
client-tool bridge, following the existing MCP continuation pattern. Electron's
`DesktopGateway` exposes only the selected work category and validates its schema,
chat ownership, capability revision and single-use execution ticket. Domain services
under `src/main/desktop` own persistent alarms and OS workflows. Electron provides
platform file opening, tray presence, notifications and power events; watched-folder
agent work starts through the existing Harnest activity interface.

Desktop resource references live alongside files and URLs in chat Context. Their
IDs and metadata are synchronized through backend receipts and survive restart.
See [desktop capabilities](desktop-capabilities.md) for delivery guarantees, native
processor requirements and supported workflows.

Browser inspection shares `src/shared/browser-semantics.ts` between the in-app isolated world and the compiled extension helper. It groups form field/submit references, infers native roles, and supplies available actions, accessible labels, validation state and select options. Visible actionable controls precede general DOM content in default pages of 100 elements, keeping the richer snapshots smaller; all elements remain reachable through pagination. Attached-browser input returns fresh refs with its new snapshot, avoiding a mandatory second read. These observations do not authorize actions or prove a website accepted an input.
