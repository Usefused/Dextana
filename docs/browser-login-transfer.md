# Website login transfer

When a website shows a sign-in form, a compact popup offers **Use login from my browser** over the page. It can be dismissed; a key icon in the browser header also opens the flow manually. Detection checks visible password/username fields, field labels and sign-in buttons, email-first pages, and SSO forms. It rechecks after page updates and includes open shadow roots and visible embedded frames, including frames from another origin. Hidden forms and ordinary navigation links do not trigger it. Dismissing a suggestion keeps it quiet for that form; a new page load or a form that disappears and returns can trigger a fresh suggestion. The key icon remains available for sites it does not recognize. Signing in directly remains available. No transfer occurs automatically, including when chat browser actions are set to auto-allow.

## Install the Chrome extension

The extension is included with Dextana, including packaged downloads. In the login dialog, expand **Need the extension?** and click **Open extension folder**. Dextana copies the bundled files into a stable `Browser Extensions/Dextana Login` directory under its application-data folder and opens it. There is no source-project folder to locate.

In Chrome, open `chrome://extensions`, enable **Developer mode**, choose **Load unpacked**, and select that **Dextana Login** folder. Pin **Dextana Browser** to the toolbar. Keep the folder in place; Chrome loads the extension from there. After updating Dextana, use **Open extension folder** to refresh this copy, then reload the extension on Chrome's extensions page.

This is a manual unpacked installation, not a Chrome Web Store installation or silent install. Chrome's Developer mode step is still required and managed browsers may disable it. See [Chrome's distribution guidance](https://developer.chrome.com/docs/extensions/how-to/distribute).

The popup checks the loaded manifest and contacts its worker before offering transfer approval. A stale or unavailable worker shows **Open extension settings** with instructions to reload, reopen and pair again, instead of exposing Chrome's missing-receiver error. Chrome clears session storage during extension reload; the connection code is not copied into durable storage to survive it. Login transfer does not depend on the browser-control debugger API.

Development reads `browser-extension` from the app checkout. Packaged builds ship it as an extra resource outside `app.asar`; runtime selects the source using `app.isPackaged`. Both copy to the same stable user-data location.

## Transfer a login

1. In Dextana, open the destination website tab and choose **Use login from my browser** in the popup, or click the key icon in the header.
2. Click **Copy connection code** in the dialog.
3. In Chrome, open **Dextana Browser**, paste the code, and click **Connect to Dextana**. Use **Open requested website** to open the requested site, then reopen the extension. It remembers the code and reconnects automatically, including when you started on Chrome’s new-tab page. The code form collapses after connection to keep the website and approval buttons visible. You can also start from an existing signed-in tab.
4. Choose cookies, local storage, and/or session storage. Cookies start selected; storage is opt-in. Click **Approve and transfer**, then grant Chrome's requested permission. If the signed-in tab differs from the login page (for example, Google Account versus Google Accounts), the popup explains the destination change and the button reads **Transfer login and open this site**. Clicking that button explicitly approves opening the displayed source site in Dextana; no separate checkbox is required. Storage stays on its own origin. To use a different account, switch accounts on the website first, then reopen the extension.
5. Return to Dextana. The approved transfer keeps running if Chrome closes its popup; Dextana automatically reveals the reloaded website and shows a completion notice. Check that the website accepted the login. A successful copy does not itself prove authentication. Continue the conversation when ready.

The approval identifies the source website and destination chat. No cookie or storage read happens before approval. The explicit transfer click hands the job to the worker before opening Chrome's permission prompt, because that prompt can destroy the popup. The worker waits up to one minute for Chrome to grant the selected cookie/site access; it captures nothing while access is missing. A declined prompt cancels the waiting job if the popup remains alive; otherwise the wait expires without capture. Closing the Chrome popup after approval does not cancel the background upload. Reopening it shows the transfer’s progress or result; an interrupted worker reports that the website must be checked before starting a new connection. Cancelling in Dextana invalidates the receiver so a pending import cannot succeed.

Matching cookie identities and storage keys are replaced. Other keys remain. The destination tab reloads, so finish unsaved work first. Cookies and local storage are shared with the destination chat's other tabs; session storage is installed only in the chosen tab. Other chats retain their isolated browser sessions. The source browser is unchanged.

## Implementation

`src/main/session-transfer.ts` runs a temporary IPv4-loopback HTTP receiver on a random port. Its random connection token is issued in the desktop dialog. The extension retains only this pairing code in Chrome session storage while opening the requested website, and clears it on cancellation or when the approved background transfer starts. It also retains a small progress/result record, containing no captured login values. Metadata requests and uploads require that token; uploads also require an extension Origin. The receiver accepts one upload, rejects unapproved categories and out-of-origin cookies, and never publishes credential values to the renderer, agent tools, saved conversation, or logs. Closing the dialog invalidates an unused connection. No public listener, external relay, login vault, or saved transfer payload is used.

`browser-extension` reads only the selected source tab's cookies from its cookie store, including HttpOnly cookies, and optional top-frame storage through an isolated script. It rechecks the source URL before upload. A different source origin requires separate explicit consent; the extension strips query/fragment metadata, and the server validates cookies against that source and stages storage at the approved source URL before loading it in the existing Dextana tab. Google-related hosts are not treated as interchangeable storage origins. Chrome asks for optional cookie/site permission at approval; the extension background worker releases this optional access after the attempt. The worker accepts internal messages only from its own popup and keeps the approved operation alive while the destination loads. The popup never starts capture merely by reconnecting. This follows Chrome’s [service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) and [session storage](https://developer.chrome.com/docs/extensions/reference/api/storage) model.

`src/main/import-login.ts` intercepts a temporary blank document at the destination URL using Electron's private debugger connection. It installs storage and cookies before loading the real website. The browser validates that the exact destination tab and URL still match and excludes concurrent agent browser actions in that chat during installation. Debugger interception is removed in `finally`. No browser debugging port is opened.

Imported state follows normal Chromium persistence and original cookie expiry. Dextana adds no login expiry, access timer, disconnect policy, or extra per-action grant. Session storage normally lasts for that browser tab; it is not restored after app restart. Persistent cookies/local storage follow the chat's existing persistent browser partition.

Transfer supports HTTPS websites and HTTP loopback sites for local development. It does not export passwords, IndexedDB, browser profiles, or partitioned cookies. Payloads are bounded to 4 MB and 1,000 entries per category. Device-bound logins, MFA, and provider policy may require direct sign-in. Installation or navigation failure can leave partially imported state; errors do not automatically retry, roll back provider activity, or claim that nothing changed.

## Tests

`tests/e2e/login-detection.spec.ts` covers plain username forms, delayed SSO dialogs, shadow-root forms, cross-origin iframe forms, hidden-field/frame false positives, and a fresh login attempt at the same URL. Frame checks have a time limit so a stalled page cannot block later detection; only detection flags and frame positions leave the page.

`tests/e2e/session-transfer.spec.ts` uses the actual Electron/Harnest application and a real Chromium extension with synthetic website data. The browser's cookie permission is pre-granted in the extension test fixture; the production source selection, approval UI, capture APIs, transport, and destination importer run unchanged. Coverage includes email-first automatic suggestions, real system clipboard copying, the 600px popup layout, automatic reconnection after destroying/reopening the popup from a new-tab flow, completion with the popup closed, immediate destination visibility, and all three categories, HttpOnly/session cookies, state before the first application script, missing approval, replay/connection cancellation, stale destinations, and keeping credentials out of agent messages. Unit tests cover scope validation, expiry preservation, category consent, duplicate inputs, concurrent upload rejection, and source navigation checks.

The same extension also supports [direct actions in an attached browser tab](user-browser.md). Chrome requests its debugger permission on installation or update; login capture still requires its separate explicit approval.

### Shared sign-in cookies

For an HTTPS page, Chrome also checks each cookie's own host and Secure flag against the extension's permissions. Access only to `myaccount.google.com` can silently omit cookies shared on `google.com`. `src/extension/login-scope.ts` uses the public suffix list (including private hosting suffixes) to request exact page and parent hosts down to the registrable domain, for both cookie schemes. The popup shows those hosts before approval. It never requests wildcard subdomains or a public suffix. Storage-only transfers retain the exact page-origin scope. Capture still filters `cookies.getAll` by the selected page URL and store, so sibling-only and unrelated cookies are excluded. Optional access is released after the attempt.

The generated `browser-extension/site-scope.js` and its license ship in the installer and the extracted extension folder. Rebuild with `npm run build` after changing the scope helper.

`tests/e2e/login-cookie-scope.spec.ts` demonstrates the omission in real Chromium with synthetic Secure and non-Secure parent cookies, then checks the corrected scope and exclusion of unrelated cookies. The transfer suite also covers reloading a stale 0.2 installation and destroying the popup before its permission callback resolves. Worker tests cover waiting without capture, grant, denial and timeout. These automated tests pre-grant synthetic browser access; the native Chrome permission dialog and actual provider acceptance must also be checked manually using the [Google acceptance flow](testing/google-login-transfer.md).
